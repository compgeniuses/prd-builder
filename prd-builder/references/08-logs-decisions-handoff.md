# 08 — Logs, decision records, progress and handoff

Logs make the work auditable and resumable. They are written **as you go**, by the workflow's
logger or by you, and they are append-only: never rewrite an old log; write a new one that
supersedes it and say so.

## Contents
1. What gets written when
2. Wave log
3. Phase-complete log
4. Decision records (including standing approvals)
5. PROGRESS.md

## 1. What gets written when

| File | When | By |
| --- | --- | --- |
| `workflow-log/000-planning-<date>.md` | After the PRD and plan are approved | Planner |
| `workflow-log/<wave>-<date>.md` | End of each wave (and a new one if a wave is reopened) | Logger / orchestrator |
| `workflow-log/<phase>-phase-complete-<date>.md` | Phase exit | `prd-phase-exit` |
| `workflow-log/<phase>-phase-exit-attempt-<date>.md` | A phase exit that failed | `prd-phase-exit` |
| `workflow-log/decisions/<date>-<slug>.md` | Every owner decision and standing approval | Orchestrator |
| `workflow-log/PROGRESS.md` | After every integration | `prd.mjs progress` |
| `SCORECARD.md` | After every wave and before phase exit | `prd.mjs scorecard --write` |
| `LOCAL-HANDOFF.md` | At every checkpoint and before any stop | Orchestrator |

## 2. Wave log

```markdown
# <wave> — <focus>  (<date>)

**Operator:** <who/what> · **Start commit:** <sha> · **End commit:** <sha> · **Pushed:** yes/no · **PR:** <link>

## Result
| Task | Outcome | Commit | Tests added | Notes |
| --- | --- | --- | --- | --- |
| P0-A05 | done | `24c7ef4` | `setup-wizard.spec.tsx` | Widened to Settings page (owner rule) |
| P0-H03 | review | `ee51aec` | `NutritionPages.test.tsx` | Merged at owner request before review |

## Gate summary (integration gate per task)
| Task | G1 | G2 | G3 related tests | G4 | G5–G7 |
| --- | --- | --- | --- | --- | --- |
| Wave gate (--base <start>) | ... | ... | ... | ... | PASS |

## Verifier notes (non-blocking)
- <task>: <note>      ← these become follow-up tasks or explicit "accepted" decisions

## Waivers and deviations
- Test waivers · scope widenings · owner overrides · tooling problems and workarounds · concurrent sessions

## Pending i18n files
## Blocked / needs review
| Task | Reason | Proposed resolution |
## Scorecard delta
Must coverage <before> → <after>; requirements newly Done: …; new gaps: …
## Next steps
1. exact commands
```

Write deviations truthfully and specifically (what happened, what was done about it, which
commit). Future readers rely on this section more than any other.

## 3. Phase-complete log

```markdown
# <phase> — <name> — phase complete (<date>)
**Commits:** <first>..<last> · **Tasks:** <done>/<total> done, <deferred> deferred · **Pushed:** yes/no

## Exit criteria
| Criterion | Met | Evidence (command → output) | Challenge |
## Phase gate        (report table)
## Probe             (report)
## Scorecard         (summary table; link to SCORECARD.md at this commit)
## Baseline before → after
## Deferred tasks (owner, target phase)
## Lessons learned / process changes
## How to start the next phase
1. node scripts/prd/prd.mjs status
2. Refine the next phase's coarse tasks into full cards (files, acceptance, test)
3. Workflow({ name: "prd-wave", args: { wave: "<P?-W1>", date: "<date>", pushTo: "prd/<P?-W1>" } })
```

## 4. Decision records (including standing approvals)

```markdown
# Decision: <title>  (<date>)
**Decided by:** <owner> · **Applies to:** <scope, e.g. all phases from P0-W1 on> · **Status:** accepted | superseded by <link>

## Context
## Rule / decision
## Conditions        (when it applies; what must still hold, e.g. "gate passes and merges cleanly")
## Applied           (table appended each time it is used: task | what | why)
## Consequences
```

Record **standing approvals** this way — e.g. "widen a task's files when the only blocker is
file ownership, provided the gate passes and the merge is clean", "accept unit evidence for a
criterion that needs a browser", "additive schema columns are allowed without migration
tasks", "model and effort per role". Agents cite them by path; the owner is not asked again.

## 5. PROGRESS.md

Generated by `node scripts/prd/prd.mjs progress`: phase table (done/deferred/blocked/in
progress/total/open wave), last completed task, blocked and review tasks with notes, next
runnable tasks per lane, current phase task table, and how to continue. Do not hand-edit.

## 6. LOCAL-HANDOFF.md — the resumption contract

Anyone must be able to continue from this file alone. Keep the top section current at every
checkpoint (before a long run, after each integration batch, before any stop):

```markdown
# Continuing the PRD (local or new session)

## 0. Current state (updated at every checkpoint)
_Last update: <date> — <one line>_

### <wave> — START HERE
Branch **`prd/<wave>`** (PR <link>, draft) = <integration> + <wave> work so far. Merge with a **merge commit**.
| Task | State | Branch / commit | Next action |
| --- | --- | --- | --- |
| P0-E04 | built, blocked by a test outside its files | `prd/P0-E04` (`714ff9d`) | widen per rule to <file>: <exact change>; gate; verify |

Gate base: <any caveat, e.g. "pass --base <integration> until the PR is merged">

Local steps:
    git fetch origin && git switch -C <integration> origin/prd/<wave>
    <install command>
    node scripts/prd/prd.mjs wave <wave>

Then: <exact Workflow(...) call with only: [...]> and <how to integrate approved branches by hand>

## 1. One-time setup        (tool versions, install, smoke gate)
## 2. Branch convention     (local alias, push target)
## 3. Rules that held       (one line each, links to decision records)
## 4. Things that went wrong (and how to avoid them)
```

Every task listed with: state, branch and sha **on origin**, and the exact next action.
"Unreviewed" and "blocked" are states, not failures — say what would move them.

## 7. Planning log

`000-planning-<date>.md`: what was produced (audit, spec, PRD, plans, ledger, tooling), key
decisions and their records, open questions, the first wave to run, and how long planning took.
